# Twilio Endpoints

## Endpoint Status

The feedback API implements `POST /webhooks/twilio/voice/start`. `/next`, call-status,
recording, and transcription callbacks are not implemented yet. `/start` only issues
the opening executable step; it does not advance the graph, execute business actions,
choose human/machine branches, or save recordings or transcripts.

## Start

`POST /webhooks/twilio/voice/start?callId=<AutomatedCalls.SystemID>`

Twilio calls this URL to obtain the opening TwiML instructions for a pre-created
attempt. Configure Twilio's initial instruction URL with this query parameter and
HTTP method `POST`.

### Request And Authentication

- Content type: `application/x-www-form-urlencoded`; maximum body size: 32 KB.
- Query: exactly one `callId`, a positive SQL integer (maximum 2147483647).
- Form fields: `AccountSid`, `CallSid` (`CA` followed by 32 hexadecimal characters),
  and `To` (an E.164 number, such as `+15551234567`). Additional Twilio form fields
  participate in signature validation and must not be discarded or modified.
- Header: `X-Twilio-Signature`, generated by Twilio using the account Auth Token.
- No bearer token is required. The public webhook is protected independently by
  its Twilio signature and configured account check.

The signature is validated using the configured public HTTPS start URL plus the
raw incoming query string and all submitted form fields. `AccountSid` must match
the configured account. Proxy host/forwarded headers are not used to reconstruct
the signed URL. Changing a query parameter or form value invalidates the signature.
When constructing a form manually, encode the leading `+` in `To` as `%2B`.

### Processing

1. Validate configuration, content type, signature, account, and request fields.
2. Read the complete `AutomatedCalls.TwiML` bundle from the central AutoCallDB.
3. In JavaScript, parse the XML with `@xmldom/xmldom`, find the declared opening
   step, generate a UUID execution ID, extract its response, and substitute every
   `{{executionId}}` placeholder. XML is not parsed or manipulated in SQL.
4. Send the prepared step ID, execution ID, response XML, and original bundle
   snapshot to `dbo.automatedcalls_Start`.
5. In one SQL transaction, lock the attempt and verify its provider, destination,
   and any previously bound provider call SID. Check the `voice:start` event before
   checking the newly prepared candidate or bundle snapshot.
6. If a valid start event exists, return its saved response and execution ID without
   changing the attempt or inserting another event. Otherwise, require a prepared
   candidate and an exact match with the current bundle before updating the attempt
   and inserting one `StepIssued` event.
7. In JavaScript, validate the returned response XML, including replayed responses,
   and return it to Twilio.

An invalid current bundle produces no candidate, but the API still invokes SQL so
that an already-issued execution can replay. With no prior event, invalid preparation
returns an error without updating the call or inserting an event. A changed bundle
between the read and transaction returns HTTP 409 without issuing stale instructions.
Bundle snapshot comparison is case-sensitive and includes trailing spaces.

Matching concurrent callbacks share one persisted execution and response. Conflicting
SIDs cannot bind the same attempt. The unique filtered event index on
`(CallId, IdempotencyKey)` is an additional database safeguard. There is no webhook
signature expiry enforced by this endpoint; replay is controlled by persisted state.

### Bundle Contract

The worker creates the attempt before dialing and resolves all ordinary variables,
call IDs, and public callback URLs. `CallFlowTemplates.TwiML` may hold the unresolved
bundle; `AutomatedCalls.TwiML` holds its personalized copy. The immutable graph stays
in `CallFlowTemplates.TemplateJSON`, referenced by the attempt's `FlowId`.

```xml
<CallFlow initialStep="reminder">
  <Step id="reminder">
    <Response>
      <Say>Hello Alex. Your device battery is low.</Say>
      <Hangup/>
    </Response>
  </Step>
  <Step id="acknowledgement">
    <Response>
      <Say>Thank you for acknowledging.</Say>
      <Hangup/>
    </Response>
  </Step>
</CallFlow>
```

This example returns only the reminder response and ends the call; the second step
is not reached automatically. A future continuation callback may use the reserved
`{{executionId}}` placeholder in a `Gather` action or `Redirect` URL, but `/next`
must be implemented before such URLs are usable.

The document must have one unnamespaced `CallFlow` root. Its nonblank `initialStep`
must be at most 200 characters and match exactly one direct, unnamespaced `Step`
child's `id`, case-sensitively. That step must contain exactly one direct,
unnamespaced `Response` child. Malformed XML, parser warnings, DTDs, unknown entities,
duplicate selected steps/responses, and unresolved placeholders in the selected
response are rejected. XML text and URL query separators must be escaped correctly.
The API validates the XML structure, not the complete Twilio verb/attribute schema.

Twilio receives only the selected `<Response>`, never the bundle. JavaScript preserves
the selected XML structure, attributes, escaped values, and CDATA, but serialization
may normalize lexical formatting. The exact serialized response is then persisted
for byte-for-byte replay. The stored bundle is not modified during progression.

### Persistence

On first issuance, the transaction binds a NULL `providerCallId`, preserves an
existing matching SID, sets `StartedDateTime` if absent, and sets `UpdatedDateTime`.
`CallStatus` changes to the configured started status only when the attempt has no
start timestamp and its status matches the configured pending status. When no pending
status is configured, the expected pending value is NULL. Other statuses are preserved.
The worker must not overwrite a different SID already bound by the callback.

The event has `EventType = 'StepIssued'`, `IdempotencyKey = 'voice:start'`, and
`EventJSON` containing `stepId`, `executionId`, `providerCallId`, and `responseTwiML`.
The call update and event insert commit together. `StepIssued` means instructions
were issued, not that audio was heard or the call completed. Queue state and tenant
data are not changed by this endpoint.

### Responses

| Status | Meaning |
| --- | --- |
| 200 | Opening or replayed TwiML; `Content-Type: application/xml`, `Cache-Control: no-store`. |
| 400 | Missing/invalid `callId`, `CallSid`, or `To`; duplicate `callId`; out-of-range call ID. |
| 403 | Missing/invalid Twilio signature, unexpected account, or non-scalar form values. |
| 404 | Attempt does not exist. |
| 409 | Provider, destination, or SID mismatch; or the bundle changed before first issuance. |
| 413 | Form body exceeds the parser's 32 KB limit. |
| 415 | Request is not form-urlencoded. |
| 500 | Invalid/unavailable instructions, corrupt replay data, or database failure. |
| 503 | Missing or invalid webhook configuration. |

Errors do not return TwiML and do not expose database error details. A 200 response
does not mean the call has completed. Caller-input validation follows authentication;
an unsigned request is rejected before its call fields are processed.

## Configuration And Deployment

| Environment variable | Purpose |
| --- | --- |
| `TWILIO_ACCOUNT_SID` | Expected account SID (`AC` plus 32 hexadecimal characters). |
| `TWILIO_AUTH_TOKEN` | Secret account Auth Token for signature validation. |
| `TWILIO_VOICE_START_URL` | Exact public HTTPS start URL, including any proxy prefix; no query, fragment, or credentials. |
| `AUTO_CALL_DATABASE` | Pool key under `dependencies.databases`; defaults to `AutoCallDB`, with no fallback to another database. |
| `TWILIO_STARTED_CALL_STATUS` | Required positive `LookUpFields.LookUpId` for started calls. |
| `TWILIO_PENDING_CALL_STATUS` | Optional positive lookup ID; omitted means NULL is the pending status. |

Equivalent `twilio` configuration keys are `accountSid`, `authToken`, `voiceStartUrl`,
`database`, `startedCallStatus`, and `pendingCallStatus`. Environment variables take
precedence. The start URL pathname must end with `/webhooks/twilio/voice/start`.

Install dependencies with `pnpm install` and deploy `database/005.sql` to AutoCallDB
using a runner that supports `GO`. Deploy both `dbo.automatedcalls_GetTwiML` and the
updated `dbo.automatedcalls_Start` together with the API; their candidate-input
contract replaces the previous SQL XML implementation. Direct callers of Start must
also supply a JavaScript-validated candidate when no event exists.

The script creates the unique filtered event index if needed. Resolve existing
duplicate non-NULL event keys before deployment; the script does not delete history.
The tables and columns from `database/001.sql` must exist. That script creates missing
tables but does not add columns to existing tables. Existing bare `<Response>` values
must be migrated to bundles before first issuance. AutoCallDB must contain the
`Client` and `LookUpFields` rows required by the existing foreign keys.

See [the running guide](../RUNNING_GUIDE.md) for column migration and local SQL test
commands. JavaScript parser and signed HTTP tests are in
`apps/notification-feedback-api/test/twilioTwiML.test.js` and
`apps/notification-feedback-api/test/twilioVoiceStart.test.js`. The isolated SQL
regression script is `database/test/automatedcalls_Start.test.sql`.
